## 2. 根因判定

- **SOURCE_ONLY vs TMF_STALE_GATED**：SOURCE_ONLY raw 40/50，TMF_STALE_GATED raw 42/50，差距只有 2 次。两臂均 `wrong_inline_loop_site=0`、`compile_fail=0`，失败主因是 agent/edit protocol 与 no-final，而不是 stale 语义边界。TMF_STALE_GATED 的源码读取确实更少（source_reads 102 vs 120，source_bytes 586,304 vs 707,518），但 raw 更高、semantic_evaluable/pass 更高（34/34 vs 20/20），因此不是“少读源码/少尝试造成的表面差异”；更像是 stale claim 被 gated/withheld 后，没有把旧 inline queue-loop 当作目标边界，行为回到源码定位。
- **PREREAD_STALE_SOURCE / STALE_DOC_CONTROL 崩盘**：PREREAD raw 2/50、STALE_DOC raw 0/50；核心信号是旧上下文诱导错误插桩位置，`wrong_inline_loop_site` 分别 43/50、45/50。categories 里的 `semantic_boundary_fail` 分别 42、43，说明多数有 hook call 的 run 都放在旧 inline loop，而不是新版本最终 `dispatchPreparedSubscriber` 边界。
- **不要误归因**：PREREAD primary `edit_protocol_fail=32`、STALE_DOC primary `edit_protocol_fail=42` 很高，很多 run 同时有 invalid path、重复 edit、final rejected 等协议噪声；这些不能直接当 TMF 语义失败。反过来，wrong_inline/correct_prepared 的 post-test placement 说明 stale context 的语义诱导是真实存在的。
- **stale_claim_withheld 字段位置**：raw JSON 内未发现每条显式 `stale_claim_withheld=true` 字段；独立聚合该字段为 0。每条 raw 的 `freshness.stale_bindings` 都记录版本/hash mismatch 字符串。原报告 `TMF_STALE_GATED stale_claim_withheld=50` 应来自 runner/arm 级配置/聚合语义，而不是 raw JSON 同名字段直接求和；这点需要在读报告时避免字段位置误解。

## 4. 结论

R50 的关键结论与原报告大体一致，但需更精确拆分原因：PREREAD/STALE_DOC 的 raw pass 低主要来自 stale boundary 将 agent 拉回旧 inline queue-drain loop；同时 protocol/no-final 噪声大量存在，不能把所有 fail 都算作语义失败。SOURCE_ONLY 与 TMF_STALE_GATED 都避开了 wrong-inline，raw 差异很小，失败多是协议层；TMF_STALE_GATED 的优势不是靠不读源码或不尝试，而是 stale claim 被门控后未暴露旧边界，从而避免 stale-context induced wrong-inline placement。
